# Test Runbook

## Overview

产物各司其职，全部落在一个需求目录里：

- **环境文档** —— 环境事实唯一源（入口、测试数据、代码库可得性、凭据来源）。
- **发现台账** —— 前面犯的错和被纠正的点，让它们继承给后面的 runbook。
- **需求快照** —— 需求正文的落盘副本：链接会变、登录态不跨会话，所以必须落盘。
- **runbook** —— 执行会话唯一的交接入口，一份 = 一条用户旅程。
- **close-out** —— 执行会话的返回件。

流程：步骤 0 建/续环境文档 → 1 需求快照 → 2 定位被测对象 → 3 按用户旅程拆场景 → 4 写 runbook → 5 交付与收尾。

核心不变量：**runbook 冷启动可执行**——一个全新会话只拿到 index、环境文档、这一份 runbook，就能不问人地把整条旅程跑完并逐步判定通过与否。**执行会话不加载本 skill，凡要求它遵守的义务随 runbook 正文走；去程有契约，回程有 close-out。** 目录布局与全部版式见 `references/artifact-layout.md`。

## 前置条件

页面操作走 chrome_devtools MCP（或同等的 CDP 通道）连**真实 Chrome 的默认 profile**：被测系统的登录态在那个 profile 里，隔离出来的新浏览器每次都要重登，且挡掉验证码类交互。这条通道跑不通时先报给用户，改让用户手工提供页面路径，不要静默换成"根据经验推测页面"。

## 输出语言

面向用户的提问、选项、交付文案跟随用户当前语言，只输出一种。本文件的中文是给 agent 的指令，不是给用户的台词。

## Token 纪律

一次只读取当前步骤要用的模板或小节；不要在对话里复述 runbook 正文，给绝对路径。文件里已记录的事实自己读、自己实测，不回问用户。

## 步骤 0 —— 环境文档与发现台账

环境事实集中在一份环境文档，一个需求一份、全程同一份、只增量改。版式在 `references/artifact-layout.md`，语义在这里：

- **内容**：被测入口（URL 或菜单路径、所需登录态、当前状态、探测方式）｜测试数据（需要什么、怎么造、怎么找、当前是否存在、清理与隔离方式）｜**代码库清单**（绝对路径 + 角色；判"有码／无码"就读这张表）｜凭据按来源（配置文件里的记路径与键名，用户在对话里口头给的按原样记下并写用途，两头都没有的进显式缺口）｜浏览器与宿主状态（Chrome profile 是否已登录、CDP 通道是否可用、能否新建会话）。
- **读**：各步骤与执行会话读正文、不抄正文，只引用条目号（`E-01`／`D-01` 写入时递增，增删行不挪号）。换会话开工先重读。
- **写**：只有两类增量动作，都只改对应条目、不整体重写——① 任一会话实测证伪了已记事实，就地改那一条（注记里留下原值）并追加一行台账；② 编排会话在步骤收口时把本步新实测到的事实与台账条目提升进来。
- **显式缺口**：查不到又拿不到的事实不许留空，也不许靠默认答案绕过，写成条目并带 `最迟复核时点｜影响哪些 runbook｜是否阻塞`。只有**被测入口**和**代码库清单**两类阻塞本轮测试；凭据、造数方式的缺口可以带着继续，到复核时点必须核一次，到期未回填就记进台账。
- **发现台账**：一行一个"以后会因此改变做法"的东西，三种触发当场各加一行——用户纠正了 agent、实测证伪了既有认知（含假通过的步骤）、用户拍了此前没有的口径（类型填"决策"）。命中已有结论的答复不记，那是流水账。跑测试与写 runbook 前先读全部标「坑」的条目。

该需求已有环境文档时读它并增量补，不新建第二份。**完成判据：** 环境文档与 index 已建且路径确定，「被测入口」「代码库清单」两张表非空、或已列成阻塞缺口并向用户提问。连目录都建不出来（不可写、路径没定）才报 `blocked`，不进入步骤 1。

## 步骤 1 —— 需求快照

把需求正文落盘成 `requirement.md`，版式见 `references/artifact-layout.md`：

- 用户给文本 → 原样落盘，出处写"用户口述"。
- 用户给禅道这类链接 → 用真实 Chrome 已登录态打开读取正文，落盘时记 URL、抓取时间、需求编号；页面读不到（未登录、无权限、结构不认识）时请用户贴正文，不许靠猜测补全需求。
- 拆出**验收条款清单**：一条 = 一个可判定的要求，保留原文编号。这是步骤 3 覆盖对照的左列，也是后续判断"漏测"的尺子。
- **完成判据：** 快照正文非空且带出处与抓取时间；验收条款每条有编号；原文里模糊或缺失的要求逐条列进「需求疑点」并转成用户问题或显式缺口，不许在快照里替用户补齐。

## 步骤 2 —— 定位被测对象

按代码可得性分叉，结论一律标**定位三态**：`代码确认`（附文件:行）／`实探观察`（只在浏览器里看到的）／`用户口述`。

- **有代码**：读环境文档的代码库清单，按需求关键词检索前端路由、菜单配置、页面组件、接口路径、界面文案，得到入口路径与相关代码位置。静态检索到"有这个页面"不等于"能进得去"，可达性靠路由 + 菜单入口 + 实测三者之一确认。
- **无代码**：用浏览器打开环境文档记录的入口，沿菜单、搜索、面包屑实探找页面；每条结论只能标 `实探观察`，并在交付文案里明说这份 runbook 的失败诊断上限只到现象层（见步骤 5）。
- 产出候选清单：每条 = 页面/功能名 + 入口路径 + 三态标记 + 代码位置（若有）+ 相关验收条款编号。
- **完成判据：** 清单每条都有入口路径与三态标记；每条验收条款至少对应一条清单项，对不上的记为显式缺口或转成用户问题；`实探观察` 且影响某条旅程可达性的已写进环境文档缺口表。

## 步骤 3 —— 按用户旅程拆场景

一份 runbook = 一条用户旅程：从入口走到**一个可判定的业务终态**。终态判据必须是页面或数据上能观测到的事实（"列表出现这条新记录且状态=已完成"），不是"功能正常"。

- 切分依据是终态不同，不是页面不同：同一条旅程跨多个页面也合成一份；终态不同的才分开。
- 边界、异常、非法输入**不单开 runbook**，挂进所属旅程的「变体」段落，只写与主流程的分岔点和差异步骤。
- 在 index 写覆盖对照表：`验收条款编号 → R<n>#<步骤号>`，左列来自步骤 1 的条款清单，逐条填。
- **完成判据：** 每条验收条款都指向至少一个步骤；每个步骤都能反指条款编号或显式标"探测附带"；每条旅程各有独立终态判据；旅程份数与候选清单的差项有说明（合并且记录，或列成未覆盖项交用户裁决）。

## 步骤 4 —— 写 runbook

版式、各列填法、执行契约正文全在 `references/templates/runbook.md`，那里是执行期义务的唯一语义源：照抄实例化、替换占位符，**不改写规则**，也不在 index 或环境文档里再抄一份义务。

写每一步时守两条门：

- **死值或取法**：每个输入值要么是写死的值，要么写清怎么取到一个满足条件的值（"输入一个已存在的手机号"不算取法，要写成"在列表第一行取该记录的手机号并记为 `M`"）。敏感值按模板规则引用环境文档条目号。
- **观测点填得出来**：预期要写成能与观测逐字比对的形式（文案、URL、状态值、条数）。填不出观测点的那一步说明定位没做够——回到步骤 2 补查，仍无结果就记成显式缺口并问用户，不许写成"检查功能正常"。

取证按 `references/browser-evidence.md` 的命名与等待规则写进「取证」列。

- **冷启动自检（每份 runbook 写完就做）：** 判据是"一个全新会话只凭 index + 环境文档 + 这一份 runbook，不问人能跑完并逐步判定"。通读全文，凡出现的名称（页面、按钮、字段、账号、数据、目录）要么在环境文档有出处、要么在本 runbook 内有取法、要么是执行会话当场观测得到的；契约与正文里不许残留 `<占位符>`，绝对路径逐条确认真实存在。出现任一需要新会话"猜"的地方，就地改成步骤。
- **完成判据：** 每份 runbook 通过冷启动自检；每步的「观测点／预期／取证」三列填到位且预期可判定（「结果」列留 `☐` 给执行会话）；执行契约已按模板全文实例化在该份文档头部；变体段落各带分岔步骤号；文档头部基线（需求快照路径＋日期）已填。

## 步骤 5 —— 交付与收尾

交付文案一句话说清三件事，交给用户：

1. runbook 路径清单（绝对路径）与各自的定位三态、诊断上限；
2. 开法：新开一个会话，粘贴"按 `<runbook 绝对路径>` 跑完这条旅程，先读环境文档 `<路径>`"；
3. 回程：跑完或卡住后回到本会话说 `R<n> 跑完了，请读 <close-out 路径> 收尾`。回程这句话不告诉用户就等于没有回程。

多份 runbook 时按序开：它们共用同一个真实 Chrome，并发会互抢标签页与登录态。**首跑校准**——第一轮先挑最短的那条旅程跑，凡是执行会话卡在文档层面的（找不到控件、要的值没给、路径不存在）都算 runbook 缺陷，改文档重发，不记成被测系统的 bug；这类纠正当场记台账（类型=坑）。

**收尾（收到回传后的入口动作，按序做完才算收尾）：** 读 close-out；读不到就按 runbook 的结果列报实际进度，并往台账追加一行"执行会话未产出 close-out"——不许把"没产出"当作"没问题"。核 close-out 必含行的存在性；新事实与纠错按步骤 0 的写入规则归类提升；需要回写需求快照的遗漏就地补进快照并在 index 记日期；未确认的变更先转达用户。

**增补（全流程随时可用，不重跑）：** 用户或执行会发现环境/需求遗漏时，只改对应那一条（环境文档增量改、需求快照补段落并记时间、runbook 改受影响步骤并在头部更新核对日期），已跑出的 close-out 是历史快照，不回改。

## 恢复（换会话继续编排）

先读 `docs/testing/<topic>/index.md`，再读环境文档，然后只读本次要用的 runbook 与需求快照相关小节；与对话历史冲突时以文件为准。index 里的旅程状态、覆盖对照、待解问题即续接点，不重跑步骤 0–4。续接信息不构成执行授权——跑测试由用户开执行会话。
