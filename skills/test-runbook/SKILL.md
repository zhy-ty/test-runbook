# Test Runbook

> 调用方式：本 skill 由人工触发（输入框 `/test-runbook` 或提及）。正文进入上下文后就照本文件执行，**不要再调用 Skill 工具去"激活"自己**——在 Qoder 里那条调用会固定返回 `cannot be activated via the Skill tool due to disable-model-invocation`，属预期噪音，不是安装问题。

## Overview

产物各司其职，全部落在一个需求目录里：

- **环境文档** —— 环境事实唯一源（入口、测试数据与备份、代码库可得性、凭据来源、浏览器通道）。
- **发现台账** —— 前面犯的错和被纠正的点，让它们继承给后面的 runbook。
- **需求快照** —— 需求正文的落盘副本：链接会变、登录态不跨会话，所以必须落盘。
- **runbook** —— 执行会话唯一的交接入口，一份 = 一条用户旅程。
- **脚本原语库** —— 可复用的导航/造数脚本卡与可执行用例；**落在被测项目，skill 只带格式与决策规则**，不存放实际脚本。
- **close-out** —— 执行会话的返回件。

流程：步骤 0 环境文档与通道探测 → 1 需求快照 → 2 定位被测对象 → 2.5 执行档决策（实探/合段断言/脚本档）→ 3 拆场景与定轮次 → 4 写 runbook → 5 交付（生成会话到此停手）→ 执行会话跑 → 回传收尾。

核心不变量有三条：

1. **runbook 冷启动可执行**——一个全新会话只拿到 index、环境文档、这一份 runbook，就能不问人地把整条旅程跑完并逐步判定。**执行会话不加载本 skill，凡要求它遵守的义务随 runbook 正文走；去程有契约，回程有 close-out。**
2. **同一份 runbook 在哪个会话跑都出同一结论**——通道、轮次、执行档、取证级别都在生成阶段定死并写进文档；执行期只读结论，不按当轮环境临时换通道或改细节。环境变了按"实测证伪"增量改那一条并记台账，不临场切换。
3. **生成与执行分离**——生成会话写完 runbook 就停手；同会话自跑只能由用户在交付后显式选择，并标自检轮，不能当作冷启动证据。

目录布局与全部版式见 `references/artifact-layout.md`。

## 前置条件

需要一个能驱动**真实浏览器**的控制通道（MCP 工具，或本地 Playwright 工程这类可执行通道），被测系统的登录态在用户日常用的那个 Chrome profile 里。具体是哪一种通道在步骤 0 探测并写进环境文档#浏览器通道，本文件不假定通道名。**不要因为当前会话没有 Playwright MCP 就判定本机没有 Playwright**——本地工程也算候选，见步骤 0。通道跑不通时先报给用户，或改由用户手工提供页面路径；不要静默换成"根据经验推测页面"，也不要为了跑通擅自改用户的 MCP 配置或代装工具。

## 输出语言

面向用户的提问、选项、交付文案跟随用户当前语言，只输出一种。本文件的中文是给 agent 的指令，不是给用户的台词。

## Token 纪律

一次只读取当前步骤要用的模板或小节；不要在对话里复述 runbook 正文，给绝对路径。文件里已记录的事实自己读、自己实测，不回问用户。探测类动作自带预算：通道只测候选的最多两个，其余记 `未验证`；脚本段单段 ≤5 步或 ≤30s。

## 步骤 0 —— 环境文档、台账与通道探测

环境事实集中在一份环境文档，一个需求一份、全程同一份、只增量改。版式在 `references/artifact-layout.md`，语义在这里：

- **内容**：被测入口（URL 或菜单路径、所需登录态、当前状态、探测方式）｜测试数据（需要什么、怎么造、怎么找、当前是否存在、**备份快照、处置方式、文件副作用**）｜**代码库清单**（绝对路径 + 角色；判"有码／无码"就读这张表）｜凭据按来源（配置文件里的记路径与键名，用户在对话里口头给的按原样记下并写用途，两头都没有的进显式缺口）｜**浏览器通道**｜显式缺口。
- **通道探测**（进入步骤 1 前做一次，结论固化，之后不再重选）：按可信度取三档，冲突时以第一档为准——
  1. **当前会话已挂载的工具**：这是唯一能代表"现在真能用"的依据。agent 自己看不见工具清单时，用一次只读实探代替（打开入口或列标签页），以实探成功为可用。
  2. **配置文件**：只用来解释"为什么没挂上"，不能当作可用依据。常见位置：`~/.qoder/settings.json` 的 `mcpServers`、`~/.claude.json` 的 `mcpServers`、被测项目根的 `.mcp.json`。
  3. **本地可执行物/工程**：Playwright 的浏览器缓存目录、`node_modules/@playwright/test`、`npx playwright --version`、项目里的 `playwright.config.*`。**本地 Playwright 工程即使没有对应 MCP，也算候选通道**——只要它能在本机驱动真实 Chrome；不要因为当前会话工具列表里没有 Playwright 就跳过。
  探测本地 Playwright 的顺序：先在被测项目根或用户给的 e2e 工程目录找 `playwright.config.*`；再在该目录跑 `npx playwright --version` 和一次 `--list` 或 smoke；读配置里的 `channel`（如 `chrome`）与登录态方案（storageState／独立 profile）。浏览器缓存目录为空不代表没装——配置成 `channel: 'chrome'` 时本来就不下载 Chromium。
  写进环境文档#浏览器通道：通道名、可用与否、能力（语义定位／自动等待／脚本导出／脚本执行）、验证方式与结果、登录态来源、本地工程的路径与版本。**只测候选的最多两个**（优先：当前已挂 MCP + 一个本地 Playwright 工程），其余记 `未验证`，不要为了探测把所有 MCP 跑一遍。
- **工具推荐门**：只有"本轮所需能力缺失、且本需求确实需要"（例如要做脚本档但没有能导出脚本的通道）时才提一次推荐，并给三样：收益、代价、**验证命令**；附一句"装完要新开会话才刷新工具列表"。只给可复制命令，不代装、不代改配置。**本机已有本地 Playwright 但只是没接成 MCP 时，推荐的是"把工程接进步骤 0 的通道表/补登录态"，不是重装 Playwright。**
- **读**：各步骤与执行会话读正文、不抄正文，只引用条目号（`E-01`／`D-01`／`C-01` 写入时递增，增删行不挪号）。换会话开工先重读。
- **写**：只有两类增量动作，都只改对应条目、不整体重写——① 任一会话实测证伪了已记事实，就地改那一条（注记里留下原值）并追加一行台账；② 编排会话在步骤收口时把本步新实测到的事实与台账条目提升进来。
- **显式缺口**：查不到又拿不到的事实不许留空，也不许靠默认答案绕过，写成条目并带 `最迟复核时点｜影响哪些 runbook｜是否阻塞`。只有**被测入口**和**代码库清单**两类阻塞本轮测试；凭据、造数方式的缺口可以带着继续，到复核时点必须核一次，到期未回填就记进台账。
- **发现台账**：一行一个"以后会因此改变做法"的东西，三种触发当场各加一行——用户纠正了 agent、实测证伪了既有认知（含假通过的步骤）、用户拍了此前没有的口径（类型填"决策"）。命中已有结论的答复不记，那是流水账。跑测试与写 runbook 前先读全部标「坑」的条目。

该需求已有环境文档时读它并增量补，不新建第二份。**完成判据：** 环境文档与 index 已建且路径确定；「被测入口」「代码库清单」两张表非空、或已列成阻塞缺口并向用户提问；「浏览器通道」表非空且本轮通道已选定（本地 Playwright 候选也要有探测结论，未测的标 `未验证`）；测试数据表里凡需要造数的行都已填"备份快照""处置方式"与"文件副作用"。连目录都建不出来（不可写、路径没定）才报 `blocked`，不进入步骤 1。

## 步骤 1 —— 需求快照

把需求正文落盘成 `requirement.md`，版式见 `references/artifact-layout.md`：

- 用户给文本 → 原样落盘，出处写"用户口述"。
- 用户给禅道这类链接 → 用环境文档记的通道打开已登录页面读取正文，落盘时记 URL、抓取时间、需求编号；页面读不到（未登录、无权限、结构不认识）时请用户贴正文，不许靠猜测补全需求。
- 拆出**验收条款清单**：一条 = 一个可判定的要求，保留原文编号。这是步骤 3 覆盖对照的左列，也是后续判断"漏测"的尺子。
- **完成判据：** 快照正文非空且带出处与抓取时间；验收条款每条有编号；原文里模糊或缺失的要求逐条列进「需求疑点」并转成用户问题或显式缺口，不许在快照里替用户补齐。

## 步骤 2 —— 定位被测对象

按代码可得性分叉，结论一律标**定位三态**：`代码确认`（附文件:行）／`实探观察`（只在浏览器里看到的）／`用户口述`。

- **有代码**：读环境文档的代码库清单，按需求关键词检索前端路由、菜单配置、页面组件、接口路径、界面文案，得到入口路径与相关代码位置。静态检索到"有这个页面"不等于"能进得去"，可达性靠路由 + 菜单入口 + 实测三者之一确认。
- **无代码**：用环境文档记的通道打开入口，沿菜单、搜索、面包屑实探找页面；每条结论只能标 `实探观察`，并在交付文案里明说这份 runbook 的失败诊断上限只到现象层（见步骤 5）。
- 产出候选清单：每条 = 页面/功能名 + 入口路径 + 三态标记 + 代码位置（若有）+ 相关验收条款编号。
- **完成判据：** 清单每条都有入口路径与三态标记；每条验收条款至少对应一条清单项，对不上的记为显式缺口或转成用户问题；`实探观察` 且影响某条旅程可达性的已写进环境文档缺口表。

## 步骤 2.5 —— 执行档决策门

先选执行档，再写步骤。三档从轻到重，默认实探：

1. **实探**：默认。没有前端源码，或预期落不到渲染层断言时用它。
2. **合段断言**：有前端源码，且一段连续步骤的预期能落到渲染层断言，且通道能执行脚本（如 CDP `evaluate_script`）时用。它不要求脚本导出，也不产出可复用用例；一段 inline 脚本按步骤号返回 `observed`。
3. **脚本档**：在合段断言的基础上，通道还具备语义定位、自动等待、脚本导出，且这段动作值得沉淀为可复用原语时用。实际脚本/卡片落在被测项目，不放在本 skill 仓库。

三档共同的三条硬规则（开哪一档都生效）：

1. **只交 `observed`，不交 `verdict`。** 判定必须由你逐条比对「预期」后写进「结果」列；脚本自己宣布通过不算数。
2. **只许断言渲染层**：可见 DOM、aria 片段、toast、URL、控件禁用态。禁止读接口响应或前端 store 数据代替界面观测——数据源会呈现用户看不到的东西，直接制造假通过。
3. **单段 ≤5 步或 ≤30s**，超时拆段；一段按 runbook 步骤号返回结构化结果，任一步不符即停在该步、后续标 ⏭。长嵌套等待会让 CDP 超时，那是工具链现象，不是被测缺陷。

脚本卡格式、probe 与失效判据见 `references/automation-scripts.md`；实际脚本与原语卡**一律放被测项目**（卡片 `docs/testing/_lib/...`，可执行用例放项目的 e2e 目录）。**复用只限导航与造数这类前置步骤；读数类原语只能作为观测辅助，不能替判定步下结论。**

## 步骤 3 —— 按用户旅程拆场景与定轮次

一份 runbook = 一条用户旅程：从入口走到**一个可判定的业务终态**。终态判据必须是页面或数据上能观测到的事实（"列表出现这条新记录且状态=已完成"），不是"功能正常"。

- 切分依据是终态不同，不是页面不同：同一条旅程跨多个页面也合成一份；终态不同的才分开。
- 边界、异常、非法输入**不单开 runbook**，挂进所属旅程的「变体」段落，只写与主流程的分岔点和差异步骤。
- **轮次**：默认 `冒烟`——主流程全跑，「变体」整段关闭（步骤保留、标 `本轮未开启`），失败后只回归失败步与该条款的判定步；`全量` 才加变体、边界与全流程回归，必须由用户显式开启。轮次写进 index 与每份 runbook 头部。轮次只关变体与回归范围，**不裁剪主流程**。
- 在 index 写覆盖对照表：`验收条款编号 → R<n>#<步骤号>`，左列来自步骤 1 的条款清单，逐条填。状态只取这几种：`✅实测`（本轮当场观测到）、`代码确认`（只读到代码，未实测）、`观测缺失`、`本轮未开启（原因 + 开启条件）`、`未覆盖（原因 + 裁决人）`、`未跑`。`✅实测` 不能用在只有代码确认或单样本不足的条款上；样本受限时在状态后注 `样本限制：...`。不许留空。
- **完成判据：** 每条验收条款都指向至少一个步骤或写明本轮未开启；每个步骤都能反指条款编号或显式标"探测附带"；每条旅程各有独立终态判据；旅程份数与候选清单的差项有说明（合并且记录，或列成未覆盖项交用户裁决）；轮次已写进 index；覆盖状态取值合法，`✅实测` 都有证据路径，`代码确认` 与样本限制已注明。

## 步骤 4 —— 写 runbook

版式、各列填法、取证规则与执行契约正文全在 `references/templates/runbook.md`，那里是执行期义务的唯一语义源：照抄实例化、替换占位符，**不改写规则**，也不在 index 或环境文档里再抄一份义务。

写每一步时守两条门：

- **死值或取法**：每个输入值要么是写死的值，要么写清怎么取到一个满足条件的值（"输入一个已存在的手机号"不算取法，要写成"在列表第一行取该记录的手机号并记为 `M`"）。敏感值按模板规则引用环境文档条目号。
- **观测点填得出来**：预期要写成能与观测逐字比对的形式（文案、URL、状态值、条数）。填不出观测点的那一步说明定位没做够——回到步骤 2 补查，仍无结果就记成显式缺口并问用户，不许写成"检查功能正常"。预期列也不许写"可能为空／不判失败"这类免责句；需求没规定或用户拍板的差异，移到「需求外观察」或「变体」并注明来源，步骤的预期仍写实际可判定的值。

取证按模板内联的「取证规则」写进「取证」列：先在「本旅程速览」列出判定步；判定步与失败步全量，其余步骤合并成段内证据，步骤表里非判定步只能写"并入 snap-R<n>-起-止.md"或 `—`，不得单独开文件。本轮通道具体怎么取、有哪些坑，按 `references/browser-evidence.md` 及其通道实现文件。开了合段断言或脚本档的旅程，在「脚本段」表里列出段号、模式、覆盖步骤、被测项目内的原语卡/用例路径与失效判据。

- **冷启动自检（每份 runbook 写完就做）：** 判据是"一个全新会话只凭 index + 环境文档 + 这一份 runbook，不问人能跑完并逐步判定"。通读全文，凡出现的名称（页面、按钮、字段、账号、数据、目录、通道）要么在环境文档有出处、要么在本 runbook 内有取法、要么是执行会话当场观测得到的；契约与正文里不许残留 `<占位符>`，绝对路径逐条确认真实存在，且**不出现 skill 安装目录的路径**（证据目录与脚本卡都在被测项目内）。出现任一需要新会话"猜"的地方，就地改成步骤。
- **完成判据：** 每份 runbook 通过冷启动自检；每步的「观测点／预期／取证」三列填到位且预期可判定（「结果」列留 `☐` 给执行会话）；判定步清单与取证列一致，非判定步没有单步证据文件；执行契约已按模板全文实例化在该份文档头部；变体段落各带分岔步骤号与本轮是否开启；文档头部基线（需求快照路径＋日期）、轮次、通道、执行档已填。

## 步骤 5 —— 交付（生成会话到此停手）

**硬门：生成 runbook 的会话不得继续执行这些 runbook。** 写完最后一份 runbook 后，本会话只输出交接文案并停手，**同一轮里不得再调用任何浏览器通道**。把交接文案给用户，由用户开新会话执行。

同会话自跑的唯一合法路径：用户在**看到交接文案后的下一轮**明确选择"本会话自检轮"。不许把开场的"跑下测试流程""执行过程中缺什么都可以说"当成这个选择，也不许由生成会话自己推断。用户选择自检轮时，先复述代价：环境事实都在上下文里，跑通只能证明文档可读，不能证明新会话能跑；然后在 index 与 close-out 标 `自检轮（不构成交付验证）`，并在最终汇报的第一句写"本轮为自检轮，冷启动未验证；以下'通过'仅指本会话内观测"。

交付文案一句话说清四件事，交给用户：

1. runbook 路径清单（绝对路径）与各自的定位三态、诊断上限、轮次、执行档；
2. 本轮执行方式：`新会话执行（推荐，验证冷启动）`；如果你确实想在本会话自检，回复"在本会话自检轮"，并知道它不构成交付验证；
3. 可直接粘贴的一句：`按 <runbook 绝对路径> 跑完这条旅程，先读环境文档 <路径>`；
4. 回程：跑完或卡住后回到本会话说 `R<n> 跑完了，请读 <close-out 路径> 收尾`。回程这句话不告诉用户就等于没有回程。

多份 runbook 时按序开：它们共用同一个真实 Chrome，并发会互抢标签页与登录态。**首跑校准**——第一轮先挑最短的那条旅程跑，凡是执行会话卡在文档层面的（找不到控件、要的值没给、路径不存在）都算 runbook 缺陷，改文档重发，不记成被测系统的 bug；这类纠正当场记台账（类型=坑）。

**收尾（收到回传后的入口动作，按序做完才算收尾）：** 读 close-out；读不到就按 runbook 的结果列报实际进度，并往台账追加一行"执行会话未产出 close-out"——不许把"没产出"当作"没问题"。核 close-out 必含行的存在性（含数据处置与备份路径、文件副作用、需求外观察、证据清单）；新事实与纠错按步骤 0 的写入规则归类提升；需要回写需求快照的遗漏就地补进快照并在 index 记日期；未确认的变更先转达用户。

**收尾一致性核对（必须做）：** index 的每个 `✅实测` 都要能在 close-out 找到对应证据路径；close-out 标了 `代码确认／观测缺失／未实测` 的，index 不得写 `✅实测`；close-out 的缺口必须出现在 index 的未覆盖项或待解问题。发现冲突时以 close-out 的细项为准，改 index 并记一行台账。

**需求外观察：** 执行中发现需求没写、但看起来不对的现象，不阻塞主流程，写进 close-out 的「需求外观察」行（现象｜是否需求内｜用户决定｜处置状态）。用户要求修复时，按 R4c 只回归受影响失败步/判定步；改动清单、回归证据和状态写进 close-out 的后续增补，**未回归前相关条款不能标 `✅实测`**。close-out 是历史快照，后续改动只追加 delta，不回改原段落。

**增补（全流程随时可用，不重跑）：** 用户或执行会发现环境/需求遗漏时，只改对应那一条（环境文档增量改、需求快照补段落并记时间、runbook 改受影响步骤并在头部更新核对日期），已跑出的 close-out 是历史快照，不回改。

## 恢复（换会话继续编排）

先读 `docs/testing/<topic>/index.md`，再读环境文档（含#浏览器通道与轮次），然后只读本次要用的 runbook 与需求快照相关小节；与对话历史冲突时以文件为准。index 里的旅程状态、覆盖对照、待解问题即续接点，不重跑步骤 0–4。续接信息不构成执行授权——跑测试由用户开执行会话。
