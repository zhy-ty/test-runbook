# 取证实现（生成侧）

取证**规则**（级别、命名、判定口径）只在一处：`references/templates/runbook.md` 的「取证规则」段，执行会话读的是 runbook 里内联的那一份。本文件只回答两件事：本轮用哪条通道、该通道下怎么把证据取到。执行会话不需要读它。

## 选通道

先读环境文档#浏览器通道，只从标了"本机可用"的行里选，并且满足本旅程要的证据类型：

- 只需要读文字、URL、条数、状态值 → 任意能读 DOM 或 aria 的通道都够。
- 需要视觉判定（颜色、红字高亮、排版、图表形状）→ 通道必须能截图，且截图要能和文字证据对上。
- 开了脚本档 → 通道必须同时具备语义定位、自动等待、脚本导出三项；缺一项就关掉脚本档，改实探（结论写进 runbook 头部）。

通道的可用性结论只在步骤 0 探测一次并固化。执行期发现通道不可用，停下报用户，不临场换通道——换了通道，证据格式和等待行为都会变，同一份 runbook 的前后两轮就不可比。

## 通用要求

- 一条证据要能独立回答"这一步看到的值是什么、和预期差在哪"，不依赖对话上下文。
- 先等再判：判"没出现"之前，按该步的动作等一次并记等待时长，再重试同一观测；两次都无才判 ✗。
- 读文字优先于截图；截图只作辅证，除非该步的预期本身就是视觉属性。
- 虚拟列表、骨架屏、延迟渲染的页签都会制造"元素不存在"的假失败——这三类观测点写 runbook 时就要带上"等什么出现"的前置条件。

## 按通道的实现

- `chrome_devtools`（CDP）：见 `references/browser-evidence.chrome-devtools.md`。
- 具备语义定位 + 自动等待 + 脚本导出的通道（如 Playwright 类 MCP）：接入时新增一份同构的实现文件，只写该通道的取法与坑，不改上面的规则。没有实测过的通道不许先写"应该可以"。
