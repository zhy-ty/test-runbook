# Runbook 模板（执行期义务的唯一语义源）

一份 runbook = 一条用户旅程。本文件定义版式、各列填法与执行契约正文；语义只在这里写一次。实例化时照抄正文、替换占位符，**不改写规则**；index、环境文档、需求快照里都不再抄一份义务。

## 实例化规则

1. 所有 `<...>` 占位符换成本旅程的实际值。填不出就是显式缺口：写进环境文档缺口表并按 `needs-input` 处理，不许留空，也不许凭默认答案填。
   契约 R3 的两个路径有固定来源：取证目录按 `references/artifact-layout.md` 的 `runbooks/evidence/R<n>-<日期>/` 填绝对路径，浏览器取证细则填本 skill 安装目录下 `references/browser-evidence.md` 的绝对路径——执行会话不加载本 skill，靠这两条路径读规则。
2. 执行契约正文放在每份 runbook 的头部并**全文照抄**。执行会话未必加载本 skill，指向它读不到的地方比重复更糟；宁可重复正文，也不留悬空引用。
3. 步骤号在本文件内唯一，`R<n>#<步骤号>` 是 close-out、覆盖对照、变体分岔点共用的引用格式。
4. 每份 runbook 只写一条旅程的终态；跨页面可以合并成同一份，终态不同才另开一份。
5. 「结果」列由执行会话当场写回，生成时留 `☐`。
6. 口令、token、真实客户数据一律**不进 runbook**，只写"见环境文档#凭据 <条目号>"这类出处；步骤里需要的死值若是敏感数据，先按写入规则落进环境文档，runbook 引用条目号。

## 版式

```markdown
# R<n> <旅程一句话：从哪儿进、做成什么> — <topic>

> 含内部入口与凭据引用的过程产物，勿提交；要入库由用户拍板。

## 本旅程速览
- 终态判据：<页面或数据上可观测到的事实，一条>
- 入口：<URL 或"从 X 菜单进入 Y">（出处：环境文档#被测入口 <条目号>）
- 定位三态：<代码确认（附文件:行）／实探观察／用户口述>；诊断上限：<能读到代码则到根因／读不到则只到现象层>
- 前置数据：<必须已存在什么；怎么造或怎么找>
- 基线：需求快照 <绝对路径> @<日期> ｜ 本 runbook 最后核对于 <日期>

## 步骤
| # | 动作 | 观测点 | 预期 | 取证 | 结果 |
|---|------|--------|------|------|------|
| 1 | 打开 <URL>（环境文档#被测入口 <条目号>） | 页面标题区文案 | 出现"…"，且 URL 以 <路径> 结尾 | snap-R<n>-01 | ☐ |
| 2 | 在「<字段名>」输入 <死值，或写明取法：在列表第一行取该客户的手机号，记为 M> | 同字段回显 + 下方提示区 | 提示"…"，无红色报错 | snap-R<n>-02 | ☐ |

（每步都要能被一个不认识这个系统的会话照做：动作里带具体控件名与所在页面，预期里带可比对的具体值。）

## 变体
| 变体 | 分岔自 | 差异步骤 | 预期 | 结果 |
|------|--------|----------|------|------|
| <非法输入／边界值／异常路径> | R<n>#<步骤号> | <差异步骤> | <可判定预期> | ☐ |

## 未覆盖与假设
- <本旅程没覆盖的验收条款、带缺口的步骤，各注明环境文档缺口表条目号>
```

## 执行契约正文（原样实例化后放在 runbook 头部）

```
## Execution Contract — <topic> / R<n>

本 runbook 是执行会话唯一的交接入口；执行会话不加载任何编排 skill，以下义务对本旅程全程有效，与你的默认习惯冲突时以本节为准。

R1 开工前必读：环境文档 <绝对路径>（被测入口、凭据、代码库清单、宿主能力）与需求快照 <绝对路径> 的对应条款。
   文件里已记录的事实（URL、账号用途、服务状态、代码库路径）自己读取或按记录的探测命令实测，不得转成用户问题。
R2 逐步判定：只有当场观测到的事实与「预期」一致，才在该步「结果」列写 ✅ 并当场写回本文件。
   不一致 → 按 R4 停下。观测不到、或要靠"看起来正常"才算过的 → 在该步写 `观测缺失` 并同样走 R4。
   没跑到的步骤标 ⏭，不空着——空着分不清是没跑还是漏写。
R3 每步取证：按「取证」列命名保存快照/截图到 <绝对目录>（命名与等待规则见 <浏览器取证细则绝对路径>）。没有证据的步骤不算跑过。
R4 失败分叉：停在该步，其后所有步骤标 ⏭（它们的结论不可信），然后按序做完——
   a. 先原地复现一次该步以排除偶发（同样的动作、同样的观测点）；仍失败才继续 b，偶发成功则在该步标 `偶发` 并继续旅程。
   b. 判代码可得性：读环境文档#代码库清单。路径存在且可读 → 检索到文件:方法级，写出根因假设与支撑证据；
      不可得 → 只写到现象层（复现步骤 + 观测事实 + 与预期的差异），在 close-out 标 `无码可查` 并停下向用户报告，不许编造代码级原因。
   c. 定位结论先报用户，得到同意才改代码；改完必须回归本 runbook **全流程**（不是只跑失败那一步），并把改动清单与回归结果写进 close-out。
   d. 无论是否修复，当场往发现台账 <绝对路径> 追加一行（序号按现有最大号递增，类型填 坑／环境事实／决策）。
R5 实测证伪了环境文档已记的某条事实时，就地增量改那一条（注记里留下原值）并按 R4d 追加台账；除此之外不得重写或复制该文件。
   发现需求本身有遗漏或与页面冲突，写进 close-out 的「需回写需求快照」行，不自行改需求。
R6 收尾写 close-out：<runbook 同目录>/close-out/R<n>-<YYYY-MM-DD>.md，必含——
   步骤完成度 x/y（含 ✅／✗／偶发／观测缺失／⏭ 各计数）、每条 ✗ 的现象与证据路径、
   代码定位结论 或 `无码可查`、改动清单（无则写"无"）、回归结果、
   「本 runbook 的新事实或显式缺口：无」或清单（每条带台账序号 `L-xxx`）、「需回写需求快照：无」或清单。
   "无／不确定／blocked"都是合法值：不许为好看编内容，也不许为了填满清单编造发现。
R7 交代回程：本旅程跑完（或卡住）后向用户交代最后一件事——回到生成这份 runbook 的会话（编排会话）说
   "R<n> 跑完了，请读 <close-out 绝对路径> 收尾"，或直接把你这段输出粘回去。编排会话不会自己看见你的工作目录变化。
```

（变体的切分与合并规则在 `SKILL.md` 步骤 3；本模板只给分岔点的列序。）
