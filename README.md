# test-runbook

仓库地址：**<https://github.com/zhy-ty/test-runbook>**

一个把**需求变成可交接的页面测试流程文档**的 skill。你一次给全前置环境和需求内容，它落一份环境文档、把需求切成验收条款、找到要测的页面和功能，再按"一条用户旅程一份文档"写出若干份 runbook。每份 runbook 都写成新会话照着做就能跑完的操作步骤——第一步打开冰箱门，第二步把大象放进去，第三步关上冰箱门，每一步都带"看哪里、期待看到什么、留什么证据"。

产出以**文档**为主：执行者是 agent（你新开的那个会话），不是 CI。有前端源码且步骤能落到页面断言时，可以在**被测项目里**沉淀可复用的脚本卡/用例（导航、造数、读数），但验收结论仍由执行者当场判定，脚本不宣布通过。**实际脚本和卡片不放进 skill 仓库**——skill 只带格式与决策规则。

## 这个 skill 不承诺什么

- **不是测试框架，也不接 CI。** 默认由 agent 当场操作浏览器，证据是页面快照与截图。脚本档只是把导航和造数这类重复动作收成原语，不是 `npm test` 那种回放；判定步仍然要逐条看。实际脚本/卡片落在被测项目，本仓库不托管。
- **只覆盖 Web 页面操作。** 接口、SQL、后端日志、单元测试都不在主步骤格式里。真要扩，`references/templates/runbook.md` 的列定义是唯一要动的地方。
- **不保证读得到你的需求系统。** 需求链接靠真实浏览器里的已登录状态打开抓取；读不到（未登录、无权限、页面结构不认识）就退回来请你贴正文，不会替你猜需求。
- **不会自动开执行会话。** 宿主通常不能替用户来回开会话，所以去程靠你粘贴一句"按 `<路径>` 跑完"，回程靠你说一句"R1 跑完了，请读 close-out 收尾"。这句回程话没告诉用户，就等于没有回程。
- **生成会话不会替你跑。** 0.2.1 起这是硬门：写完 runbook 就停手交给你，同一轮不得再开浏览器。同会话自跑只能在看到交付文案后、由你**显式选择**"自检轮"；它不构成交付验证——环境事实都在上下文里，跑通证明不了新会话能跑。
- **0.2.1 修的是 0.2.0 一次真实首跑暴露的问题。** 那次暴露了生成会话自跑、取证未真正分级、脚本档在 CDP 上被误关、本地 Playwright 未被探测、index 与 close-out 状态冲突等；这一版修了这些，但 Playwright 通道与合段断言仍需下一次实跑验证。第一次用请把 runbook 当草稿：跑不通时先怀疑文档有没有写清，再怀疑被测系统。

## 你需要准备的前置环境

| 项目 | 缺失的后果 |
| --- | --- |
| 被测入口：URL 或菜单路径 | **阻塞**。没有入口就没有第一步。 |
| 被测代码库的绝对路径（前端／后端，能给就给） | 决定失败诊断上限：有码 → 失败能查到文件与方法级；无码 → 只写到现象层并停下问你。有前端源码也是开合段断言/脚本档的前提。 |
| 测试账号与角色（说明用途即可，口令按来源记录） | 不阻塞本轮，但会卡在某一步的登录态上。 |
| 有效测试数据：什么数据算能测、怎么造或怎么找；要造数时的备份与处置方式 | 步骤里写不出"取法"，只能反过来问你，冷启动就破了。 |
| 一条能驱动真实浏览器的通道（MCP，或本地 Playwright 工程；有语义定位/自动等待/脚本导出更好） | 只能由你手工描述页面路径，定位结论全部降级为`实探观察`。本地 Playwright 即使没接成 MCP 也算候选，步骤 0 会探测。 |
| 需求正文或需求链接 | 没有需求就没有验收条款，也无从判断漏测。 |

这些全部落进 `environment.md`。后续每个会话只引用路径和条目号，不抄正文；发现遗漏走"增补"，只改对应那一条。

## 工作流

```
步骤 0: 环境文档 + 发现台账 + index + 浏览器通道探测（MCP 与本地 Playwright 工程，最多两个候选）
步骤 1: 需求快照 → 验收条款清单（这是后面判断"漏测"的尺子）
步骤 2: 定位被测对象 → 定位三态（代码确认／实探观察／用户口述）
步骤 2.5: 执行档决策（实探／合段断言／脚本档；有前端源码 + 渲染层断言至少合段断言）
步骤 3: 按用户旅程拆 runbook + 定轮次（默认冒烟：主流程全跑，变体与全流程回归关）
步骤 4: 写 runbook（冷启动自检 + 死值或取法 + 契约与取证规则全文内联）
步骤 5: 交付后停手 → 你开新会话跑 → close-out 回来收尾
        同会话自检必须由你在下一轮显式选择；多份按序开，第一轮先跑最短那条做首跑校准
```

## 一轮怎么用

1. 本会话调用 `/test-runbook`，把前置环境和需求内容一次给它。得到 N 份 runbook 和一段交付文案。
2. 默认**新开一个会话**，粘贴：`按 <runbook 绝对路径> 跑完这条旅程，先读环境文档 <绝对路径>`。
   只有你明确回复"在本会话自检轮"，生成会话才会继续跑；它会标自检轮，且不能当作冷启动验证。
3. 跑完或卡住后，回到第 1 步那个会话（编排会话）说：`R1 跑完了，请读 <close-out 绝对路径> 收尾`。

一份 runbook 对应一个会话。多份 runbook 别并发开——它们共用同一个真实 Chrome，会互抢标签页和登录态。

## 产物

```
docs/testing/
  YYYY-MM-DD-<topic>/
    index.md                        # 续接索引：路径、覆盖对照、旅程状态、轮次、通道、执行档
    environment.md                  # 环境文档：环境事实唯一源（含内部地址与凭据）
    discoveries.md                  # 发现台账：前面犯的错和被纠正的点
    requirement.md                  # 需求快照：原文 + 验收条款 + 需求疑点
    runbooks/R1-<slug>.md           # 一份 = 一条用户旅程，头部带执行契约
    runbooks/close-out/R1-<日期>.md # 执行会话的返回件
    runbooks/evidence/R1-<日期>/    # 快照、截图、造数前的 data-backup/
  _lib/<module>/<primitive>.md      # 原语卡（资产，跨需求复用）
tests/e2e/<module>/<primitive>.spec.ts  # 可执行用例（项目自己的 e2e 目录）
```

**脚本归属：** `_lib/` 的卡片和 `tests/e2e/` 的可执行用例都在**被测项目**里（或项目指定的独立 e2e 工程），随项目入库；本 skill 仓库只带格式与规则，不放任何项目脚本、路由、选择器或账号。

**两类文件的提交口径不同。** `YYYY-MM-DD-<topic>/` 是过程产物，默认不进提交清单；`_lib/` 是资产，应该入库。在被测项目里给忽略规则开口子时不能只写 `!docs/testing/_lib/`（父目录被排除时反选不生效），要写成：

```
docs/testing/*
!docs/testing/_lib/
```

## 关键机制（想改规则前先读这段）

- **冷启动**是每份 runbook 的验收判据：一个全新会话只凭 index + 环境文档 + 这一份 runbook，不问人就能跑完并逐步判定。杀掉"换会话就跑不动"这个根因的门叫**死值或取法**——每个输入值要么写死，要么写清当场从哪儿取（"输入一个已存在的手机号"不算取法）。
- **确定性**是第二条判据：通道、轮次、取证级别都在生成阶段定死并写进文档，执行期只读结论。同一份 runbook 两次跑通道不同，证据就不可比，"漏测"和"复现"都无从谈起。
- **假通过**由两条规则挡住：只有当场观测到的事实与「预期」逐字一致才写 ✅；脚本只许读渲染层（可见 DOM／aria／toast／URL），读接口或前端 store 会看到用户看不见的东西。
- **生成/执行分离**：写完 runbook 就停手，同一轮不得再开浏览器；同会话自检只能由你在交付后显式选择，并标"自检轮（不构成交付验证）"。
- **轮次**默认冒烟：主流程全跑，变体和全流程回归关闭；要跑全量由你显式开。冒烟不裁剪主流程，只关变体和回归范围。
- **执行档三选一**：实探（默认）／合段断言（CDP inline，不要求导出）／脚本档（语义定位 + 自动等待 + 脚本导出）。执行档在生成阶段定死，执行期不改。
- **取证分级**：判定步与失败步留全量证据，中间步骤按段合并；模板里的非判定步只能写"并入 snap-R<n>-起-止.md"或 `—`，不逐 step 开文件。
- **覆盖状态**只取 `✅实测／代码确认／观测缺失／本轮未开启／未覆盖／未跑`；代码确认和单样本不足不能写成 ✅，index 必须与 close-out 对得上。
- **需求外观察**：需求没写但看起来不对的现象，写 close-out 的「需求外观察」；你要求修复时只回归受影响步骤，未回归前相关条款不能标 ✅。
- **失败分叉**按代码可得性走两条路：有码查到文件:方法级、报你同意才改、改完只回归失败步与该条款的判定步；无码只写现象并标 `无码可查` 停下。
- **造数先备份**：动数据前先导出当前状态（以造数主键为根、关联表一起），结束按预先写好的处置方式回滚或删除，不把清理语句留给你当交付物；会生成/覆盖文件的动作，按环境文档「文件副作用」列备份或取得你的显式豁免。
- **通道探测含本地工程**：本地 Playwright 工程即使没有对应 MCP 也算候选；探测看 `playwright.config.*`、`npx playwright --version`、登录态方案，不靠浏览器缓存目录判断装没装。
- **首跑校准**把文档缺陷和被测系统的 bug 分开：执行会话卡在"找不到控件、要的值没给、路径不存在"上，算 runbook 缺陷，改文档重发，不当 bug 记。
- **脚本原语先验后用**：复用前必须跑 probe（路由、控件、关键字面），不过就标 `脚本失效`、回落实探并记台账；复用只限导航与造数，判定步必须本轮观测。
- **语义唯一源**：执行期义务与取证规则在 `references/templates/runbook.md`；编排语义在 `SKILL.md`；产物版式在 `references/artifact-layout.md`；脚本卡格式在 `references/automation-scripts.md`；通道实现细则在 `references/browser-evidence*.md`。各管一段，别处不许再抄。

## 依赖

**没有外部 skill 依赖**，本仓库自带环境文档、发现台账与取证规则的定义。运行侧需要一条能驱动真实浏览器的通道（MCP 或本地 Playwright 工程），登录态在你日常用的 Chrome profile 里；具体通道在步骤 0 探测并写进环境文档。本地 Playwright 工程不要求接成 MCP。

本 skill 是**手动调用**的（frontmatter 里 `disable-model-invocation: true`）：只有你打出 `/test-runbook` 才会触发，模型不会自己想起来用它，因此它也不占常驻上下文。副作用是：在被 @ 提及或 `/` 调用后，agent 若再尝试用 Skill 工具"激活"它，会收到 `cannot be activated via the Skill tool due to disable-model-invocation`——这是预期噪音，不是安装失败；SKILL.md 开头已写明不要再调。

## 方式一：CC Switch

CC Switch 按固定目录发现 skill，本仓库的 `skills/` 这一层就是给它用的。

| 字段 | 值 |
| --- | --- |
| 仓库地址 | <https://github.com/zhy-ty/test-runbook> |
| Owner | `zhy-ty` |
| Name | `test-runbook` |

## 版本与更新

当前 **0.2.1**：生成/执行分离硬门、本地 Playwright 探测、实探/合段断言/脚本档三档、取证分级真正落到模板、覆盖状态词表、需求外观察闭环、文件副作用备份。

0.2.1 改变了 runbook 契约字段（R1–R9、执行档、判定步/取证列、覆盖状态、close-out 需求外观察与证据清单），**0.2.0 及 0.1.0 生成的 runbook 不能直接沿用**：字段缺失会让执行会话按错误的口径判定，请重新生成。

**发布前检查：** committed 文档里引用的 `references/*.md` 必须都能在 `git ls-tree` 里找到。0.2.0 曾漏提交两个新 reference 文件，导致换机/发布时悬空引用。

```bash
for f in $(grep -rhoE 'references/[A-Za-z0-9._/-]+\.md' README.md skills | sort -u); do
  git cat-file -e "HEAD:skills/test-runbook/$f" 2>/dev/null || echo "MISSING $f"
done
```

本仓库暂时没有 `docs/problem-log.md`。在它建起来之前，**改规则的动因写进 commit message**——加一条规则就说清它来自哪一次卡住，删一条就写下理由和日期，否则下一个人只会看到规则、看不出它为什么不能退回原来的写法。
