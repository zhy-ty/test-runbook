# test-runbook

仓库地址：**<https://github.com/zhy-ty/test-runbook>**

一个把**需求变成可交接的页面测试流程文档**的 skill。你一次给全前置环境和需求内容，它落一份环境文档、把需求切成验收条款、找到要测的页面和功能，再按"一条用户旅程一份文档"写出若干份 runbook。每份 runbook 都写成新会话照着做就能跑完的操作步骤——第一步打开冰箱门，第二步把大象放进去，第三步关上冰箱门，每一步都带"看哪里、期待看到什么、留什么证据"。

产出是**文档**，不是脚本。执行者是 agent（你新开的那个会话），不是 CI。

## 这个 skill 不承诺什么

- **不生成自动化测试代码，也不接 CI。** 步骤由 agent 当场用浏览器执行，证据是 CDP 快照和截图。要回归得再跑一次会话，不是 `npm test` 那种回放。
- **只覆盖 Web 页面操作。** 接口、SQL、后端日志、单元测试都不在步骤格式里。真要扩，`references/templates/runbook.md` 的列定义是唯一要动的地方。
- **不保证读得到你的需求系统。** 禅道这类链接靠真实 Chrome 的已登录 profile 打开抓取；读不到（未登录、无权限、页面结构不认识）就退回来请你贴正文，不会替你猜需求。
- **不会自动开执行会话。** 宿主通常不能替用户来回开会话，所以去程靠你粘贴一句"按 `<路径>` 跑完"，回程靠你说一句"R1 跑完了，请读 close-out 收尾"。这句回程话没告诉用户，就等于没有回程。
- **0.1.0 还没有一条真实需求跑通过。** R1–R7 执行契约是设计推演的产物，"首跑校准"没发生过。第一次用请把它当草稿：跑不通时先怀疑 runbook 本身有没有写清，而不是先怀疑被测系统有 bug。

## 你需要准备的前置环境

| 项目 | 缺失的后果 |
| --- | --- |
| 被测入口：URL 或菜单路径 | **阻塞**。没有入口就没有第一步。 |
| 被测代码库的绝对路径（前端／后端，能给就给） | 决定失败诊断上限：有码 → 失败能查到文件与方法级；无码 → 只写到现象层并停下问你。 |
| 测试账号与角色（说明用途即可，口令按来源记录） | 不阻塞本轮，但会卡在某一步的登录态上。 |
| 有效测试数据：什么数据算能测、怎么造或怎么找 | 步骤里写不出"取法"，只能反过来问你，冷启动就破了。 |
| Chrome 已登录被测系统 + CDP 通道可用（`chrome_devtools` MCP） | 只能由你手工描述页面路径，定位结论全部降级为`实探观察`。 |
| 需求正文或需求链接 | 没有需求就没有验收条款，也无从判断漏测。 |

这些全部落进 `environment.md`。后续每个会话只引用路径和条目号，不抄正文；发现遗漏走"增补"，只改对应那一条。

## 工作流

```
步骤 0: 环境文档 + 发现台账 + index（只有被测入口、代码库清单两类缺口阻塞本轮）
步骤 1: 需求快照 → 验收条款清单（这是后面判断"漏测"的尺子）
步骤 2: 定位被测对象 → 定位三态（代码确认／实探观察／用户口述）
步骤 3: 按用户旅程拆 runbook（一条旅程 = 一个可判定终态；边界与异常走「变体」段落，不另开文档）
步骤 4: 写 runbook（冷启动自检 + 死值或取法 + 执行契约全文实例化到文档头部）
步骤 5: 交付 → 你开新会话跑 → close-out 回来收尾
        多份按序开；第一轮先跑最短那条做首跑校准
```

## 一轮怎么用

1. 本会话调用 `/test-runbook`，把前置环境和需求内容一次给它。得到 N 份 runbook 和一段交付文案。
2. **新开一个会话**，粘贴：`按 <runbook 绝对路径> 跑完这条旅程，先读环境文档 <绝对路径>`。
3. 跑完或卡住后，回到第 1 步那个会话（编排会话）说：`R1 跑完了，请读 <close-out 绝对路径> 收尾`。

一份 runbook 对应一个会话。多份 runbook 别并发开——它们共用同一个真实 Chrome，会互抢标签页和登录态。

## 产物

```
docs/testing/YYYY-MM-DD-<topic>/
  index.md                        # 续接索引：路径、覆盖对照、旅程状态
  environment.md                  # 环境文档：环境事实唯一源（含内部地址与凭据）
  discoveries.md                  # 发现台账：前面犯的错和被纠正的点
  requirement.md                  # 需求快照：原文 + 验收条款 + 需求疑点
  runbooks/R1-<slug>.md           # 一份 = 一条用户旅程，头部带执行契约
  runbooks/close-out/R1-<日期>.md # 执行会话的返回件
  runbooks/evidence/R1-<日期>/    # CDP 快照与截图
```

**把 `docs/testing/` 加进被测项目的 `.gitignore`** 是默认做法：环境文档里有内部地址，凭据表里可能有用户口头给的口令。要入库由你拍板；跨需求都要留存的结论应该落进 ADR、词汇表或你们自己的用例库，而不是只活在过程文档里。

## 关键机制（想改规则前先读这段）

- **冷启动**是每份 runbook 的验收判据：一个全新会话只凭 index + 环境文档 + 这一份 runbook，不问人就能跑完并逐步判定。杀掉"换会话就跑不动"这个根因的门叫**死值或取法**——每个输入值要么写死，要么写清当场从哪儿取（"输入一个已存在的手机号"不算取法）。
- **假通过**由步骤格式挡住：只有当场观测到的事实与「预期」逐字一致才写 ✅；要靠"看起来正常"才算过的，标 `观测缺失` 走失败分叉。
- **失败分叉**按代码可得性走两条路：有码查到文件:方法级、报你同意才改、改完回归全流程；无码只写现象并标 `无码可查` 停下。
- **首跑校准**把文档缺陷和被测系统的 bug 分开：执行会话卡在"找不到控件、要的值没给、路径不存在"上，算 runbook 缺陷，改文档重发，不当 bug 记。
- **语义唯一源**：执行期义务只在 `references/templates/runbook.md`；环境文档与台账的读写规则只在 `SKILL.md` 步骤 0；产物版式只在 `references/artifact-layout.md`；取证细则只在 `references/browser-evidence.md`。四处各管一段，改行为只改对应那一份，别处不许再抄。

## 依赖

**没有外部 skill 依赖**，本仓库自带环境文档与发现台账的定义。运行侧需要一条 CDP 通道：`chrome_devtools` MCP（或同等的浏览器控制工具），连真实 Chrome 的默认 profile——被测系统的登录态在那里。

本 skill 是**手动调用**的（frontmatter 里 `disable-model-invocation: true`）：只有你打出 `/test-runbook` 才会触发，模型不会自己想起来用它，因此它也不占常驻上下文。

## 方式一：CC Switch

CC Switch 按固定目录发现 skill，本仓库的 `skills/` 这一层就是给它用的。

| 字段 | 值 |
| --- | --- |
| 仓库地址 | <https://github.com/zhy-ty/test-runbook> |
| Owner | `zhy-ty` |
| Name | `test-runbook` |
| Branch | `master` |
| Subdirectory | `skills` |

添加仓库后安装 `test-runbook`，没有需要额外拉的上游仓库。

> 如果你把默认分支改成 `main`，记得同步这张表，以及你自己的 CC Switch 配置。

## 版本与更新

当前 **0.1.0**：六个步骤的编排、runbook 模板的 R1–R7 执行契约、四类产物版式。

本仓库暂时没有 `docs/problem-log.md`。在它建起来之前，**改规则的动因写进 commit message**——加一条规则就说清它来自哪一次卡住，删一条就写下理由和日期，否则下一个人只会看到规则、看不出它为什么不能退回原来的写法。等第一条真实需求跑通、契约被实测改过之后，再把动因整理成 problem-log。
